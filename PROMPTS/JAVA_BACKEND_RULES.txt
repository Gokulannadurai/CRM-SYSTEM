================================================================================
                                NAMING CONVENTIONS
================================================================================

1.  CLASS NAMING:
    - Use PascalCase for class names (e.g., UserService, CustomerController)
    - Use descriptive names that clearly indicate the class purpose
    - Avoid abbreviations unless they are widely understood (e.g., HTTP, URL, API)
    - Suffix classes with their type: Service, Controller, Repository, Entity, DTO, Config

2.  METHOD NAMING:
    - Use camelCase for method names (e.g., getUserById, createCustomer)
    - Use verb-noun combinations for action methods
    - Use descriptive names that clearly indicate the method's purpose
    - Avoid generic names like "process", "handle", "doSomething"

3.  VARIABLE NAMING:
    - Use camelCase for variables (e.g., customerId, userEmail, totalCount)
    - Use descriptive names that clearly indicate the variable's purpose
    - Avoid single-letter variables except for loop counters (i, j, k)
    - Use meaningful names for boolean variables (e.g., isActive, hasPermission)

4.  CONSTANT NAMING:
    - Use UPPER_SNAKE_CASE for constants (e.g., MAX_RETRY_ATTEMPTS, DEFAULT_PAGE_SIZE)
    - Group related constants in separate classes or enums
    - Use descriptive names that clearly indicate the constant's purpose

5.  PACKAGE NAMING:
    - Use lowercase for package names (e.g., com.company.project.service)
    - Use reverse domain name convention for base packages
    - Organize packages by functionality, not by layer

================================================================================
                                CODE STRUCTURE & ORGANIZATION
================================================================================

6.  CLASS STRUCTURE ORDER:
    - Static final fields (constants)
    - Instance fields
    - Static initializer blocks
    - Instance initializer blocks
    - Constructors
    - Public methods
    - Protected methods
    - Private methods
    - Inner classes

7.  METHOD LENGTH & COMPLEXITY:
    - Keep methods under 20 lines of code
    - Maximum cyclomatic complexity of 10 per method
    - Extract complex logic into private helper methods
    - Use early returns to reduce nesting

8.  CLASS RESPONSIBILITY:
    - Single Responsibility Principle: Each class should have one reason to change
    - Maximum 200 lines per class
    - Extract large classes into smaller, focused classes
    - Use composition over inheritance

9.  PACKAGE ORGANIZATION:
    - Group related classes in the same package
    - Use sub-packages for different layers (controller, service, repository)
    - Keep package structure flat (max 3-4 levels deep)
    - Use feature-based packaging for large applications

                                IMPORT STATEMENTS
================================================================================

14. IMPORT ORGANIZATION:
    - Never use wildcard imports (*)
    - Group imports in the following order:
      1. Java standard library imports
      2. Third-party library imports
      3. Application-specific imports
    - Use static imports sparingly and only for utility methods
    - Remove unused imports

15. IMPORT BEST PRACTICES:
    - Import specific classes, not entire packages
    - Use static imports for frequently used utility methods
    - Avoid importing classes from implementation packages
    - Keep imports organized and clean
